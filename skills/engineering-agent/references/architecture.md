# Engineering Agent 架构与组件关系

## 整体架构

```
                    ┌─────────────────────────────────────┐
                    │         用户交互层 (User)            │
                    └───────────────┬─────────────────────┘
                                    │ prompt
                                    ▼
┌───────────────────────────────────────────────────────────────────┐
│                     Engineering Agent (编排层)                    │
│                                                                   │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌────────┐ │
│  │  分类器  │→│ 澄清器  │→│ 规划器  │→│ 分发器  │→│ 验收器  │ │
│  └─────────┘  └────┬────┘  └─────────┘  └────┬────┘  └───┬────┘ │
│                    │                          │            │      │
│                    ▼                          ▼            ▼      │
│             grill-me-with-doc            Sub-agents     自我批判  │
│                                       Scripts/Skills             │
└──────────────────────────────────────────┬───────────────────────┘
                                           │ 写回
                                           ▼
                    ┌─────────────────────────────────────┐
                    │         资产层 (Asset Store)        │
                    │  skills / rules / memory / hooks    │
                    └─────────────────────────────────────┘
```

## 组件职责

### 编排层组件

| 组件 | 职责 | 对应阶段 |
|------|------|---------|
| **分类器** | 判断任务复杂度，决定是否走完整工程化流程 | Step 0 |
| **澄清器** | 六维需求澄清（目标/约束/输入/输出/边界/验证） | Step 1 |
| **规划器** | 产出执行计划、任务分解、验收标准、人工卡点 | Step 2 |
| **分发器** | 生成任务包，选择执行方，调度执行顺序 | Step 3 |
| **验收器** | 自我批判 + 结构化验收 + 回退处理 | Step 4 |
| **写回器** | 资产沉淀判断 + 写入对应位置 | Step 5 |

### 执行方

| 执行方 | 类型 | 适用场景 | 示例 |
|--------|------|---------|------|
| **Skill** | 能力包 | 已有成熟流程覆盖的领域 | lark-doc, excel-xlsx |
| **Sub-agent** | 智能体 | 需要理解推理的非确定性任务 | 代码生成、文档写作、研究调研 |
| **Script** | 脚本 | 确定性、重复性任务 | 文件处理、数据计算、格式转换 |
| **Hook** | 事件钩子 | 由系统事件触发的固定动作 | SessionStart 注入上下文、SessionEnd 蒸馏 |

### 资产层

| 资产类型 | 存储位置 | 生命周期 |
|---------|---------|---------|
| Skills | `~/.claude/skills/` 或项目 `.claude/skills/` | 长期，版本化 |
| Rules | `~/.claude/rules/` 或项目 `.claude/rules/` | 长期，稳定后很少变 |
| Memory | `~/.claude/projects/<slug>/memory/` | 长期，持续更新 |
| Hooks | `~/.claude/hooks/` | 长期，稳定后很少变 |

## 数据流向

```
用户 prompt
    │
    ├─[SessionStart hook]→ 场景上下文注入
    │
    ▼
分类器 ──简单──→ 直接执行 ──→ 输出
    │
    复杂
    ▼
澄清器 ──调用──→ grill-me-with-doc skill
    │
    ▼ 六维摘要
规划器 ──产出──→ 执行计划 + 任务分解 + 验收清单
    │
    ▼ 计划确认
分发器 ──生成──→ 任务包 ──分发──→ sub-agent / script / skill
    │                                   │
    │                                   ▼
    │                              子任务结果
    │                                   │
    ◄───────────回传────────────────────┘
    │
    ▼
验收器 ──执行──→ 自我批判 + 验收清单检查
    │
    ├─不通过──→ 回退（重新分发 / 重新规划 / 重新澄清）
    │
    ▼ 通过
写回器 ──沉淀──→ skills / rules / memory / hooks
    │
    ▼
最终交付
```

## 关键设计决策

### 1. 为什么是 Agent 不是 Hook？

图中「分类器/澄清器/规划器/分发器/验收器/写回器」是**逻辑组件**；物理上由单个 Engineering Agent prompt + `references/` 实现，不是六个独立 agent。

工程智能体需要：
- 交互式澄清（多轮对话）
- 用户确认节点（计划确认、人工卡点）
- 动态决策（分类、回退策略）

这些都需要主动发起对话和等待用户输入，hook 是被动触发的固定动作，不适合。

### 2. 为什么子任务只给任务包不给全局上下文？

- **上下文工程原则**：上下文是有限资源，最小输入集合最优
- **隔离失败**：单个子任务的污染不影响其他任务
- **可并行**：独立任务包可以并行执行
- **可复用**：任务包格式标准化后可缓存、可重放

### 3. 为什么验收要独立于执行？

参考论文 [10] 的 handoff 视角：
- 生产方的"成功"不等于消费方的"接受"
- 执行方对任务的理解可能有偏差
- 独立验收确保结果符合消费方（工程智能体/用户）的标准

## 可扩展性

编排器的每个阶段**逻辑上**是可替换的模块；当前以单个 agent prompt 实现。
- 澄清器可以接入不同的澄清模板（技术任务、设计任务、研究任务...）
- 澄清器可以接入不同的澄清模板（技术任务、设计任务、研究任务...）
- 规划器可以接入不同的规划策略（瀑布式、迭代式、探索式...）
- 分发器可以接入更多执行方（MCP 服务、远程 API、CI/CD...）
- 验收器可以接入领域专用的检查清单
