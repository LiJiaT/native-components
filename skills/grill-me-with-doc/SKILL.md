# Grill-Me-With-Doc（需求澄清）

把模糊需求通过结构化追问收敛到可执行状态。基于 5W3H + 工程化六维框架，一次列出全部待澄清问题，避免碎片式多轮补充。

## 何时使用

**必须澄清的信号**（任一命中即触发）：
- 用户需求可以被解读成两种以上方向
- 没有明确的产出形式或交付物
- 没有验收标准或成功定义
- 涉及多步骤、多文件、多角色协作
- 用户说"先看看"、"研究一下"、"帮忙搞一下"等模糊表述
- 任务可能超出能力边界但边界不清

**可以跳过的信号**（全部满足才跳过）：
- 目标单一且明确
- 输入输出格式清晰
- 验收标准不言自明
- 单步可完成（3 个工具调用以内）
- 无未知依赖或边界风险

## 澄清六维度

围绕以下六项逐条确认，缺哪项问哪项，不缺的项直接给出你的理解供用户确认：

| 维度 | 要澄清什么 | 为什么重要 |
|------|-----------|-----------|
| **目标** | 最终要达成什么？解决谁的什么问题？ | 目标不清会导致全流程走偏，越晚补正代价越大（长程 Agent 实验：70% 处补目标 pass@3 从 0.78 降到 0.39） |
| **约束** | 时间、资源、技术栈、合规、预算、可用工具的限制 | 约束决定方案选型，遗漏会导致方案推倒重来 |
| **输入** | 已有哪些素材、数据、文档、代码？格式和位置？ | 输入质量决定输出上限，缺失输入会让执行卡壳 |
| **输出** | 交付什么形式？文件格式？粒度？放到哪里？给谁看？ | 输出形式直接影响执行路径和工作量评估 |
| **边界** | 哪些不做？做到什么程度停？避免范围蔓延 | 没有边界的任务永远做不完，也永远无法验收 |
| **验证标准** | 怎么算做完了？验收清单有哪些？谁来验收？ | 没有验收标准就没有完成的定义，交付质量不可控 |

## 操作流程

### Step 1 · 自行理解与背景收集

收到需求后，**先做一轮自己的功课**再提问，不要把能自己查到的问题抛给用户：
- 读取相关文件、查看代码结构、搜索已有上下文
- 盘点已有资产（skills、memory、rules）
- 基于已有信息给出你对六个维度的理解

### Step 2 · 结构化输出澄清问题

一次性列出所有待确认项，格式如下：

```
## 需求澄清

基于我目前的理解，先给出我的解读，标 ❓ 的是需要你确认的：

### 🎯 目标
【你的理解】❓ 需要确认：...

### 🚧 约束
【你的理解】❓ 需要确认：...

### 📥 输入
【你的理解】❓ 需要确认：...

### 📤 输出
【你的理解】❓ 需要确认：...

### 🧱 边界
【你的理解】❓ 需要确认：...

### ✅ 验证标准
【你的理解】❓ 需要确认：...

---
如果六项都明确我就直接进入规划/执行。请补充或修正。
```

**规则：**
- 已明确的项写清楚你的理解，让用户确认即可，不要开放式提问
- 未明确的项给出 2-3 个可能选项+你的推荐，降低用户决策成本
- 一次性列出全部问题，不要分轮追问（违反 5.2 避免需求碎片化原则）
- 问题数量控制在 3-8 个之间，太多会让用户疲劳；可以合并相关问题

### Step 3 · 收敛判断

用户回复后，重新评估六个维度：
- 全部明确 → 返回确认后的六维摘要，进入下一步（规划/执行）
- 仍有重大缺失 → 补充追问，但不超过 2 轮；**2 轮后仍不明确的，停止并输出《待确认清单》交用户决策，不得用假设进入执行**（§6.3：任一项未明确则不进入执行；用户明确授权"由你决定"的项视为已明确，在清单中记录授权后可继续）
- **「目标」「验收标准」两维特例**：即使用户说"由你决定"，也必须先给出具体定义/验收项草稿并获用户确认，不得仅凭"由你决定"放行

## 与 Orchestrator 的关系

本 skill 是 orchestrator 闭环的第一步（澄清阶段）。orchestrator 在收到用户输入后：
1. 先判断是否简单任务 → 简单则直接执行，跳过工程化流程
2. 复杂任务 → **调用本 skill 进行澄清**（按本 skill 的六维模板输出，orchestrator 不再内联维护副本）
3. 澄清完成 → 进入规划阶段
