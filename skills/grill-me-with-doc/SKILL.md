# Grill-Me-With-Doc（需求澄清）

把模糊需求收敛到可执行状态，并把结果落成文件：**该问的一次问清，问完有记录，不该问的不打扰**。

## 0. 唯一入口：六问判定 D1–D6

是否需要澄清只看这张表——不看关键词、不看任务大小、不看谁提的。

| 编号 | 维度 | 判定问题（YES = 已明确） | 怎么判定 | NO 的典型形态 |
|---|---|---|---|---|
| **D1** | 目标 | 能否写出「完成后，<主体> 在 <位置> 呈现 <可看见的结果>」，且不含你自编的范围/数量/对象？ | 写下这句话，与请求原文逐词核对 | 「把 X 做得更好用」「优化一下」 |
| **D2** | 约束 | 是否既无“会改变方案选型”的未决限制，又不与既有权威冲突？（权威 = registry/契约/仓库惯例/环境实际能力） | 核对权威文件；环境能力用命令实测 | 「用 agentctl 验证」（本机没这个工具） |
| **D3** | 输入 | 所需输入是否全部可定位：路径存在、内容已给、或你自查可得？是否需要用户提供尚不存在的信息？ | 列一张输入清单，逐项标“已定位/需用户提供” | 「你给的那份 URL」但没给 |
| **D4** | 输出 | 交付物路径 + 形式是否已定？来源限三种：用户明确指定 / 既有惯例（同目录同类文件）/ 任务书指定 | 看请求原文，再看同目录惯例 | 「写个报告」（到哪、什么格式） |
| **D5** | 边界 | 能否写出 ≥1 条“不做什么”，且该条来自请求或任务书（不是你为省事收缩出来的）？ | 从请求里摘“不/只/别/其它不动”类约束 | 全篇只有“要做”，没有“不做” |
| **D6** | 验证标准 | 能否列出 ≥1 条验收项，其证据是命令输出 / 文件存在 / 逐字比对（不是“看起来对”）？ | 为每条验收项指定一条可执行命令 | 「做得专业一点」 |

判定：

```
D1–D6 全部 YES
  → 不澄清（0 问）
     └ 改动 ≤2 文件 且 可逆 且 无外部副作用 → 直接执行
        （外部副作用 = push/发布/安装到用户目录/改远端/对外发送）
     └ 否则 → 出计划给用户确认（计划确认即确认点）
任一 NO
  → 澄清：问题集 = 该维对应的问题 + 无争议维度的理解确认
```

### 与 Step 0 / hook 的分工

三套规则曾并存且口径冲突，现按此归属，互不越界：

| 谁 | 管什么 | 不管什么 |
|---|---|---|
| Engineering Agent Step 0 | 走不走工程化流程 | 不决定要不要澄清 |
| `engineering-agent-classify` hook | 要不要提示主 agent 考虑工程化（旁路、fail-open） | 不是门禁，不参与判定 |
| **本 skill（D1–D6）** | **要不要澄清**（唯一判定） | 不决定流程重量 |

| Step 0 | D1–D6 | 行为 |
|---|---|---|
| 简单 | 全 YES | 直接执行，0 问，不建文件 |
| 简单 | 有 NO | **仍要澄清**（小改动但目标/验收不明） |
| 复杂 | 全 YES | **不澄清**，直接出计划（大 ≠ 模糊） |
| 复杂 | 有 NO | 澄清 → 计划 |

### 反过度澄清护栏

| # | 护栏 |
|---|---|
| P1 | D1–D6 全 YES → 0 问，任务再大也不问 |
| P2 | 用户已说“你决定/按你判断” → 记授权，不再追问；唯一例外是目标与验证标准（见 §2 O5） |
| P3 | 每题必须自带推荐答案；写不出推荐 = 功课没做够，回去查，不许抛开放式问题 |
| P4 | 同一维度一轮内只问一次；下一轮只问“由上一轮答案新解锁”的问题 |
| P5 | 单轮 >8 题必须按维度合并到 ≤8；合并后仍 >8 → 任务该拆，先问拆分 |

## 1. 一轮 = 一条 frontier

- **frontier** = 所有“前置问题已经有答案”的问题，也就是**现在就能问、不用猜**的那批。
- 依赖本轮尚未回答的问题 → 属于**下一轮**，不得混进本轮。
- 一轮内把 frontier 一次列完，列完就停，等用户回答。
- **最多 2 轮**：第 2 轮只问第一轮答案解锁的新问题。
- 问题数 = frontier 大小，上限 8。**不凑数**：只有 1 个真未知就问 1 个，不为凑 3 个编问题。

## 2. 六维：反例与已明确时的写法

判定标准见 §0 的 D1–D6；本表只给“常见反例”和“确认时该怎么写”，避免同一套判据写两遍。

| 维度 | 反例（说了等于没说） | 已明确时的写法 |
|---|---|---|
| **目标** | 「把系统做好」「优化一下」 | 「完成后 registry 中该组件 version == 1.1.0」 |
| **约束** | 「用 agentctl 验证」（工具不存在） | 「只改 3 个文件；不得动 hook」 |
| **输入** | 「那份文档」（没给路径） | 「读 tasks/04.md，已确认存在」 |
| **输出** | 「写个报告」 | 「reports/04-x/baseline.md，Markdown 表格」 |
| **边界** | 只有“要做”，没有“不做” | 「不改 gate、不改 schema、不 push」 |
| **验证标准** | 「做得专业一点」 | 「`gate.py plan` 退出码 0，且 6 份副本 hash 相同」 |

**O5 特例（不可放宽）**：约束/输入/输出/边界 可以“由你决定”并记录授权；**目标与验证标准即使授权，也必须先给出具体草稿并获用户确认**，不得只写“由你决定”就放行。

## 3. 流程

### Step 1 · 做功课（事实归你，决策归用户）

- 能自查的事实自己查（读文件、`grep`、跑命令），不抛给用户。
- 需要多路查证时可分发子 agent。
- 某个查找未完成只阻塞它的**下游问题**，其余 frontier 照常提问，不要整体等待。
- 写不出推荐答案 → 说明功课没做够，回去查。

### Step 2 · 出题 + 建草稿（同一动作）

**先建草稿再出题**：写 `reports/<task>/clarification.md`（`round: 0`、`status: drafting`），把已查到的六维理解填进去。然后按此格式出题：

```
## 需求澄清（第 1/2 轮）

回「是」即按推荐执行；只回编号也行，例如「Q2 选 B」。

❓ Q1 · 目标 —— <问题正文>
➡️ 推荐：<推荐答案 + 一句理由>

❓ Q2 · 约束 —— <问题正文>
➡️ 推荐：<推荐答案 + 一句理由>
```

规则：

- 每题编号 + 必带推荐 + 措辞让“是”= 接受推荐。
- 已明确的维度也要列，格式：`❓ Q3 · 输入 —— 我理解是 X，对吗？ ➡️ 推荐：是`。
- 一次列完 frontier，不分批。
- 不替用户回答；未确认的标“待确认”，不填默认值。

### Step 3 · 收敛（frontier 空即止）

用户回答后重算 frontier：

| 情况 | 动作 | verdict |
|---|---|---|
| frontier 空，六维全明确/授权 | 进入计划 | `proceed` |
| frontier 空，但仍有非阻塞待确认项 | 带入计划「待确认事项」 | `need-confirmation` |
| frontier 非空且 `round < 2` | 第 2 轮，只问新解锁的 | 继续 |
| `round = 2` 仍非空 | **停止**，输出《待确认清单》交用户 | `blocked` |

`blocked` 时**不得进入计划**，不得用假设开跑。**不得出现第 3 轮。**

### Step 4 · 每轮更新落盘

- 用户每次回答后**立即**更新 `clarification.md` 的 `round` / `status` / `updated_at` / 六维状态 / §2 待确认 / §3 授权 / §5 轮次。
- 不等到收尾批量补写（批量补写是和对话结论对不上的主要来源）。
- 文件与对话冲突 → 以文件为准，并立即改正对话。

### Step 5 · 交给计划

- `verdict = proceed | need-confirmation` → 进入计划阶段。
- 计划必须写 `requirement_card: {path: "reports/<task>/clarification.md", sha256: "<文件原始 sha256>"}`；gate 会校验文件存在且 hash 一致。
- 计划六要素从本文件 §6「交接给计划」抄，不重新从对话里推。
- 计划确认后澄清内容**冻结**；需修改 → 改文件 → hash 失配 → 走 Plan Change 重新确认，不得沿用旧批准。

## 4. clarification.md 模板

```markdown
---
task: <任务目录 slug>
title: 一句话标题

updated_at: 2026-10-29T14:20:00+08:00

status: answered

skipped: false
questions_total: 6

  - <读过的文件/跑过的命令>
---

| 输入 | 明确 | …… | …… |
| 输出 | 授权 | 格式由我定，已给草稿并确认 | §3-Q4 |
| 边界 | 明确 | …… | …… |

### 1.1 待展开维度（仅「待确认」「授权」「不适用」需要）

- **输出（授权）**：草稿 = ……；已确认。

## 2. 待确认项

| # | 维度 | 类型 | 现状 | 需要你确定的 | 我的推荐 |
|---|---|---|---|---|---|
| Q3 | 边界 | 阻塞 | …… | …… | …… |

## 3. 用户授权项

| # | 维度 | 用户原话 | 范围 | 时间 | 我的草稿 | 是否确认 |
|---|---|---|---|---|---|---|
| Q4 | 输出 | "格式你定" | 仅文件结构 | 2026-10-29 | 见 §1.1 | 已确认 |

## 4. 证据与引用

- 文件：<path>（sha256 前 8 位）
- 命令：<命令>
- 外部来源：<repo@commit>（license）

## 5. 轮次记录

| 轮 | 时间 | 提出 | 已回答 | 本轮新解锁 |
|---|---|---|---|---|
| 1 | …… | 6 | 6 | 0（frontier 已空） |

## 6. 交接给计划（plan 六要素初稿）

goal: 一句话目标（≥8 字）
constraints: [……]
inputs: [……]
outputs: [……]
boundaries: [……]
acceptance: [ {id, check_method, expected, evidence} ]
human_gates: [……]
```

状态取值：六维 = `明确` / `待确认` / `授权` / `不适用`；`verdict` = `proceed` / `need-confirmation` / `blocked`；`round` ∈ {0,1,2}。

## 5. 落盘合格判定（8 条，缺一不可）

| # | 检查 |
|---|---|
| 1 | frontmatter 10 个字段齐全：task / title / created_at / updated_at / round / status / verdict / skipped / questions_total / blocking_count |
| 2 | 六维表恰好 6 行，顺序为 目标 / 约束 / 输入 / 输出 / 边界 / 验证标准 |
| 3 | 每个「待确认」维在 §2 有对应行，且标了 阻塞/非阻塞 |
| 4 | 每个「授权」维在 §3 有原话 + 范围 + 草稿 + 是否确认 |
| 5 | 目标与验证标准两维不得只写“由你决定”，必须有具体草稿 |
| 6 | `verdict` 与内容一致（`proceed` ⟺ `blocking_count = 0` 且无阻塞行） |
| 7 | `round ≤ 2` |
| 8 | §6 交接块 7 个键齐全，`acceptance` 至少 1 条 |

## 6. 与 Engineering Agent 的关系

1. agent Step 0 判断走不走工程化流程；
2. agent Step 1 **调用本 skill**，并按本 skill 的 D1–D6 决定是否澄清；
3. 触发澄清时，agent **必须**产出 `reports/<task>/clarification.md`；**没有该文件不得进入 Step 2**；
4. agent 与 references **不内联维护第二份六维模板**，一律引用本 skill。
